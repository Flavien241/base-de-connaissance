# Vérifications avant le mail à la cliente

## À terminer en équipe

1. Confirmer les quatre rôles proposés autour de Flavien, chef de projet, et relire la V0.3.
2. Donner accès aux membres sur GitHub, Trello et les documents Drive. Vérifier le lien ou joindre une version exportée du cahier des charges si la cliente n’a pas accès au document partagé. Ne pas ouvrir les sources clientes au public.
3. Vérifier que les premiers fichiers sont réellement publiés sur GitHub et que les fiches Trello renvoient aux bons livrables.
4. Choisir deux ou trois disponibilités communes pour l’échange et renseigner les membres en copie. Les adresses ne sont pas inventées.
5. Préparer les questions : premier demandeur, modèle vierge et format attendu ; catalogue prioritaire et méthodes ; horizons 12/18 ; sources et clés ; habilitations et serveur.

Ces questions peuvent rester ouvertes lors de la prise de rendez-vous : le mail sert à obtenir les décisions de la cliente. Il n’est pas nécessaire de terminer le prototype avant cet envoi.

## Outils suffisants pour démarrer

- Trello : une fiche par tâche, responsable, cible, critères de fin et lien de livrable.
- GitHub : code, configurations, documentation autorisée, tests fictifs et relectures par pull request.
- Google Drive : cahier des charges collaboratif, modèles de demandeurs, fichiers de travail autorisés et grilles individuelles, avec droits adaptés.
- Un canal de discussion déjà utilisé par l’équipe et des comptes rendus datés pour les décisions. Aucun nouveau service de discussion n’est imposé.

Éviter de doubler le tableau dans GitHub Projects ou un autre outil. Une automatisation des tests dans GitHub Actions sera utile lorsque du code et des tests exécutables existent ; elle ne conditionne pas la réponse à la relance. Les guides présents sont des bases à compléter, pas des preuves de fonctionnement d’une application déjà livrée.
